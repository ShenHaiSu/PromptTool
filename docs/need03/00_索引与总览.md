## 需求原文（整理后）

1. 设计一套“较为标准”的**批量提示词导入文本格式**：用户手头通常是一整串连续的文生图提示词（英文逗号分隔的自然语言），需要交给 LLM 做拆解，LLM 返回带格式、带维度归属、已做好分段的若干“分部提示词”。
2. 完整设计**分部的逻辑**（按什么维度切、一切几段、切不准怎么办）与**分部的解析方案**（前端如何把 LLM 输出可靠地解析成结构化数据）。
3. 设计**前端交互的 UI 界面**。
4. 设计**如何根据数据库中已有的分类（`dimensions`）动态生成完整的解析提示词**（LLM System/Instruction Prompt），保证新增/改名维度后提示词自动同步，无需手写硬编码。

## 设计约束（全 Need03 通用）

- **离线优先、无外部依赖**：首版不直连任何 LLM API，采用“复制解析提示词 → 用户在任意 LLM 粘贴 → 复制 LLM 输出回本应用”的手动闭环，避免 API Key、网络、计费等强依赖；后续可在此基础上追加直连适配器。
- **向后兼容**：新增 Rust 命令沿用 `open_conn` + `Result<_, String>` 模式，DTO 保持 `camelCase`（`#[serde(rename_all = "camelCase")]`），`invoke` 参数键名与 Rust 形参 camelCase 形式一致。
- **软删除与幂等**：词条维度沿用 `is_deleted`；导入按业务键去重，多次导入同一输入无重复（幂等）。
- **单一事实来源**：维度列表以 `db_get_dimensions()` 为准，LLM 提示词、分段校验、可视化标签均由此派生。
- **UI 一致性**：新增弹窗复用 `LibraryDialog` / `SaveDialog` 的 `fixed inset-0 + Card` 与 `v-model:open` 模式，`data-testid` 命名遵循现有前缀规范。
- **文件格式版本化**：所有新 JSON 文件引入 `format` + `formatVersion` 头，便于未来演进。

## 整体链路（全览）

```
DB dimensions (14+ 自定义)
      │  dbGetDimensions()
      ▼
LLM 解析提示词生成器  ──→  用户复制  ──→  任意 LLM（ChatGPT/Claude/本地模型）
      │                                   │
      │  ① 原始整串 Prompt(s) ───────────────╯
      │                                    ↓
      │                         LLM 输出：pmf-segments JSON / Tagged Text
      │                                    │
      ▼                                    ▼
  SegmentImportDialog（向导）
   ┌──────────────┬──────────────┬──────────────┐
   │ 输入/粘贴区   │ 预览校验区    │ 导入执行区    │
   └──────────────┴──────────────┴──────────────┘
                        │
                        ▼
              批量入库 → modules（默认）
              可选：仅校验 / 入历史快照
                        │
                        ▼
              Toast + 报告 + DimensionPanel.refresh()
```

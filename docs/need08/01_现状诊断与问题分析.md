# 01 — 现状诊断与问题分析

> 结论先行：现有菜单“可用但不完整”——4 项中 1 项有视觉违规（Emoji），高频开关能力缺席（只能靠隐藏手势 `Ctrl+Click`），高危批量能力缺席（清空/迁移只能逐条删或绕路导出导入）。本次四项诉求分别对应**视觉规范、能力可发现性、批量运维闭环**三类问题。

## 2. 诉求 1：去掉生成项前的 ✨

证据：

```vue
<!-- DimensionPanel.vue:928 现状 -->
>✨ 片段批量生成</button>
```

问题：

1. **视觉规律破坏**：菜单其余 3 项均为纯文本（`批量翻译 / 复制…`），仅此一项带 Emoji，导致行高、基线、字重观感不一致；在 `text-sm` 下 Emoji 回退字体偏大，`hover:bg-accent` 时尤为刺眼。
2. **与设计系统冲突**：项目菜单/按钮文案均为文字 + 必要 `Badge`（如维度头的“单选/禁用”），Emoji 只出现在顶部预览按钮 `👁` 等极少数装饰位；右键菜单作为高频运维入口，应保持克制。
3. **测试脆弱**：`DimensionGenerate.test.ts` 按 `dim-ctx-generate-pose` 定位不受影响，但若有用 `getByText('✨ 片段批量生成')` 的写法，去 Emoji 后需同步为精确文本 `片段批量生成`（见 07 回归清单）。

决策：**纯删除 Emoji 字符，不改文案其余部分、不改 testid、不改顺序**（顺序变更留给 §4 统一做）。

## 3. 诉求 2：启用/禁用开关进右键菜单

现状能力（`DimensionPanel.vue:186-230`）：

```ts
// Ctrl+Click 直接切换禁用/启用（替代原右键菜单）
function onDimHeaderClick(e, dim){ if(isCtrlClick(e)){ void onToggleDimension(dim); return } ... }
async function onToggleDimension(dim){ /* 乐观更新 library.dimensions + dbUpdateDimension + LIBRARY_CHANGED + toast */ }
```

问题：

1. **可发现性为零**：唯一入口是 `title="Ctrl+点击可禁用 · 右键更多"` 的悬停提示，新用户根本发现不了；触屏/远程桌面下 `Ctrl+Click` 难以操作。
2. **历史包袱**：注释明示右键菜单曾有开关，后被 Ctrl 手势替代；如今右键菜单已重建（need01/need03），是时候把开关“请回来”，与 `Ctrl+Click` 双轨并存（手势保留，菜单为主）。
3. **一致性**：词条行已有 `Ctrl+Click` 切换 + 行内 `禁用 Badge`，维度头有 `禁用 Badge + opacity-60`，唯独菜单缺开关，信息与操作分离。

决策：**新增菜单项，动态文案**（见 02 §2），行为完全复用 `onToggleDimension`，不另起炉灶；`Ctrl+Click` 保留不变。

## 4. 诉求 3：清空维度内容

现状：维度内 `N` 条想全删，只能逐条点 `module-delete-{id}`（每条一次 `confirm + dbSoftDeleteModule`，`DimensionPanel.vue:526-557`），或绕路导出/删库。无批量清空能力。

风险（为什么必须审慎设计，详见 04）：

1. **不可逆**：`db_soft_delete_module` 是软删（`is_deleted=1`，`db.rs:376-384`），但前端无“回收站/恢复”入口，对用户等价于不可逆。
2. **级联**：被清空的模块若正在 `assembly.selectedItems` 中，必须同步移出已选，否则拼装 IR 悬空（`onToggleModule:232-271` 已有“禁用即移出已选”先例，清空必须同理且更强）。
3. **误删**：空维度点清空应禁用；非空维度必须二次确认（含数量与维度名），禁止一键直删。

决策：新增高危菜单项，**空维度禁用 + 非空二次确认 + 逐条软删 + 已选联动 + 乐观回滚**，样式用 `text-destructive` 与其他项区分。

## 5. 诉求 4：迁移维度（归档 + 原位重建）

诉求原文：“点击之后将当前维度的片段提示词全部迁移到维度 key 加随机防重复后缀的维度，然后新建一个同名空白维度”。

现状缺口：

1. **无任何迁移能力**：`db.ts` 只有 `dbCreateDimension / dbUpdateDimension（不含 key 变更校验）/ dbSoftDeleteDimension（要求先清空，db.rs:501-515）`，没有“搬运模块”命令；前端 `DimensionPanel.vue:424-454` 的维度编辑也不允许改 `key` 的冲突处理（仅透传，后端 `db_update_dimension:463-498` 甚至不校验 key 唯一，因为它根本不更新 key 列——见 05 §1，这是关键坑）。
2. **朴素做法不可行**：若在前端循环 `dbUpdateModule({...m, dimensionId: newId})` 搬运 `N` 条，`N=200` 即 200 次 `invoke`，无事务，中途失败即半迁；且 `key` 唯一校验在并发下有竞态。
3. **必须回答的语义问题**：归档维度的 `nameCn/sortOrder` 怎么定？新生维度的 `id` 是否复用原 id？已选/历史/规则是否受影响？随机后缀是什么字符集与长度？失败如何回滚？——全部收敛到 05。

决策：**新增 Rust 事务命令 `db_migrate_dimension`，策略为“老维度改名归档（key 加后缀、沉底）+ 原 key 原位重建空白维度”，模块行零搬运**（论证见 05 §2）。前端配专用确认对话框（非 `window.confirm`），展示归档 key 预览与影响面。

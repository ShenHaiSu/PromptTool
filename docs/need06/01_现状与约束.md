# 01 现状与约束：落盘链路与“头部”的准确定义

## 1. 当前落盘链路（`src-tauri/src/commands/image_queue/queue.rs`）

```
iq_start → scheduler_loop → worker → generate_one(agnes.rs, 取 data[0].url)
  → download_and_persist(queue.rs:534-615)
```

`download_and_persist` 现状（逐行对照 `queue.rs`）：

1. `ensure_image_dir`（`:504`，规则在 `normalize_image_dir_for:374`）：空输入 → `{data_dir}/output/images`；相对路径 → 相对 `data_dir`（strip 历史 `data/` 前缀）；绝对路径直用；`create_dir_all` + `.pmf_write_probe.tmp` 可写探测；
2. `check_disk_space`（`:476`，Windows `GetDiskFreeSpaceExW` 直调）：剩余 `< 500MB` 即 `halted(disk)`；
3. `client.get(url)` 下载，`content-type` → 扩展名（`ext_for_content_type:324`：`png/jpg/webp/gif/bmp`，非图片直接失败）；
4. 流式写 `.tmp`（`MAX_IMAGE_BYTES = 100MB`，前 16 字节留 `head` 做 `has_image_magic:337` 校验）→ `rename` 原子落盘；
5. 同名 sidecar：`final_path.with_extension("json")`（`:599`），字段（`:600-610`）：`prompt / irHash / size / ratio / model(agnes-image-2.5-flash) / imageUrl / elapsedMs / createdAt / taskId`，写失败仅记日志；
6. 文件名 `build_image_filename:310`：`{yyyyMMdd_HHmmss}_{seq}_{size}_{ratio}_{hash8}.{ext}`，`seq` 为当日计数，碰撞走 `unique_filename_in:396` 追加 `-1`；
7. 前端只消费 `filePath/imageUrl`（`src/lib/imageQueueApi.ts`、`src/stores/imageQueue.ts`），从不读 sidecar 文件内容；`iq_remove(deleteFile=true)` 顺带删 sidecar（`:1191-1196`）。

依赖现状（`src-tauri/Cargo.toml`）：无 `png/jpeg/crc` 相关 crate，只有 `reqwest/tokio/serde_json/chrono/uuid/futures/base64`。本系列按**零新依赖**设计。

## 2. 前置约束：魔数必须在 offset 0

- PNG 签名 8 字节 `89 50 4E 47 0D 0A 1A 0A`、JPG `SOI FF D8` 必须位于文件第 0 字节，这是 `has_image_magic` 与所有读图软件的判断依据；
- 在文件最前面（字面 offset 0 之前）追加任何字节都会破坏魔数 → 照片查看器/浏览器/微信/QQ 报损坏，本项目下载校验也会失败；
- 因此本系列所说的“头部”统一定义为：**文件前部的、解析器按规范跳过的元数据段**——PNG 的 `IHDR` 之后、`IDAT` 之前；JPG 的 `SOI` 之后、`SOS` 之前。这是 ExifTool / Lightroom 存 XMP 的标准做法，不是 hack。

## 3. 为什么不会乱码/报错

- PNG 解析器按 `len + type` 跳块，`iTXt` 是标准 ancillary 块，所有解析器必须识别并可忽略；`CRC` 正确则 `pngcheck -v` 无 warning；
- JPG 解析器按段长度跳 `COM/APPn`，`COM(FF FE)` 是基线 JPEG 必识段；插入点在 `SOS(FF DA)` 之前，不污染熵编码流；
- 魔数不变 → 缩略图、`<img>`、各家查看器行为不变；体积增量 = JSON 大小（通常几 KB）。

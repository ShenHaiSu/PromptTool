# 随机工厂取值范围“快照锁定”问题 — 全量修复方案

> 状态：待审阅（未落码）  
> 关联需求：need02 维度/词条 CRUD、need03 分段导入、need04 多活数据库  
> 关联代码：`src/components/BatchFactory.vue` / `src/components/DimensionPanel.vue` / `src/App.vue` / `src/stores/batch.ts` / `src/engine/random.ts` / `src/lib/db.ts` / `src-tauri/src/commands/db.rs` / `src/stores/dbRegistry.ts`  
> 决策记录：P3 触发阈值定为词库总量 200+，采用“修改行为后防抖、每 10 秒至多一次”的异步刷新策略

---

## 1 结论先行

测试人员反馈“新增词条抽不到”是必现缺陷，不是概率问题。

**一句话根因：**批量工厂的随机池在你第一次点击「随机生成」时从数据库快照一次，缓存在组件本地内存里，之后所有随机都基于这份过期快照；左侧维度面板新增词条只刷新了左侧自己的缓存，从未通知批量工厂，因此新词条在重启前永远进不了随机范围。数据库本身实时正确，错在前端双缓存失联。

本方案分四档治理，P0 当天止血、P1 同步链路、P2 切库一致性、P3 按你决策在 200+ 总量后启用防抖异步刷新，兼顾正确性与大库性能。

---

## 2 问题复述

- 启动时库里 10 条，点随机，范围是这 10 条。
- 不重启，左侧新建 1 条（左侧树可见、数据库已落盘），再点随机，新条目出现概率恒为 0。
- 重启或刷新页面后，新条目才开始出现。

## 3 取值范围是什么时候确定的

### 3.1 引擎层无状态，不决定范围

`src/engine/random.ts:27` 的 `randomAssembly(dimensions, modulesByDim, ...)` 与 `src/engine/random.ts:76` 的 `partialRandomAssembly` 均为纯函数，只对传入的 `dimensions` 与 `modulesByDim` 做 `weightedSample`，不读库、不缓存。

`src/stores/batch.ts:11` 的 `generate` / `generatePartial` 同样只消费参数并产出 `PromptIR`，不负责拉取。

### 3.2 真正决定范围的是批量工厂的首次懒加载

`src/components/BatchFactory.vue:23-37`：

```ts
const dimensions = ref<Dimension[]>([])
const modulesByDim = ref<Record<string, Module[]>>({})

async function ensureDims(): Promise<void> {
  if (dimensions.value.length) return   // 命中即直接返回，不再读库
  dimensions.value = await dbGetDimensions()
  modulesByDim.value = await dbGetAllModulesGrouped()
}
```

`src/components/BatchFactory.vue:49-70` 的 `onRandom` 每次生成前仅调用 `await ensureDims()`，然后将这份本地缓存喂给 `batch.generate`：

```ts
async function onRandom(): Promise<void> {
  await ensureDims()
  // ...
  batch.generate(dimensions.value, modulesByDim.value, lockedIds, count.value, cfg, allowNsfw.value)
}
```

因此**取值范围锁定在首次点击「随机生成」的瞬间**，之后 `dimensions.value.length > 0` 恒成立，`ensureDims` 永远走 early return。

### 3.3 为什么新增后仍抽不到

应用内存在两套完全隔离的本地缓存，没有任何同步机制：

| 持有方 | 缓存字段 | 刷新时机 | 是否通知对方 |
|---|---|---|---|
| `BatchFactory.vue:23` | `dimensions / modulesByDim` | 首次 `onRandom` | 否 |
| `DimensionPanel.vue:24` | `dimensions / modulesByDim` | `onMounted` 与每次 `onModuleConfirm / onDeleteModule / onDimConfirm / refresh` | 否 |

新增词条路径 `src/components/DimensionPanel.vue:137-164`：

```ts
async function onModuleConfirm(payload) {
  await dbCreateModule(payload.dimensionId, ...)
  // 补充 isNsfw/notes 的二次更新（若需要）
  await refresh() // 仅刷新 DimensionPanel 自身的 ref
}
```

`refresh` 在 `src/components/DimensionPanel.vue:180-205` 内确实重拉了 `dbGetDimensions` 与 `dbGetAllModulesGrouped` 并更新了左侧树，但 `BatchFactory` 的 `dimensions` 毫无感知。

同理，`src/components/DimensionPanel.vue:101` 的维度创建、`169` 的词条删除、`152` 的词条更新，均只刷新左侧。

`src/App.vue:88-100` 的 `refreshStats` 仅在 `LibraryDialog @imported` 与 `SegmentImportDialog @imported` 时被调用，且内部只做了：

```ts
dimCount.value = dims.length
moduleCount.value = total
await dimensionPanelRef.value?.refresh()
```

**没有调用 `BatchFactory` 的刷新**，普通 CRUD 更不经过 `App.vue`。

Rust 侧 `src-tauri/src/commands/db.rs:171` 的 `db_get_all_modules_grouped` 每次执行 `SELECT ... WHERE is_deleted=0`，库内数据始终实时正确，可排除后端嫌疑。

### 3.4 为什么重启能“修好”

`BatchFactory` 的 `ref` 为内存态，页面重载后 `dimensions.value.length === 0`，下次点击会重新走 `ensureDims` 的全量拉取，自然包含新词条。这也解释了测试“偶发通过”的假象。

## 4 影响面

- 手动新建/编辑/删除维度或词条后，批量工厂随机范围过期。
- 词库导入（`LibraryDialog` / `SegmentImportDialog`）后，批量工厂范围过期（`App.vue:279-287` 已接 `@imported` 但未覆盖 CRUD）。
- 业务库切换、前台库重建（`src/stores/dbRegistry.ts`）后，批量工厂仍持有旧库快照。
- 搜索过滤与 NSFW 开关不影响随机池，但会误导排查（左侧过滤后看起来“已更新”，实则随机池未更新）。

## 5 修复目标与非目标

**目标：**

1. 点击「随机生成」瞬间的取值范围必须等于数据库实时全量（含刚新增的词条、刚删除的词条、刚切换的业务库）。
2. 所有变更入口（左侧 CRUD、词库导入、分段导入、切库）后无需用户手动刷新即一致。
3. 词库总量在中小规模时保持即时一致性，总量超过 200 后自动切换为防抖异步，降低大库频繁全量拉取的开销。
4. 改动可回滚，不动表结构与 Rust 持久化逻辑。

**非目标：**

- 不引入后端随机（仍由前端 `random.ts` 负责加权抽样，便于权重与 NSFW 过滤保持一致）。
- 不改变现有交互文案与布局，仅补齐同步链路。

## 6 总体设计

### 6.1 核心思想

- **读时必新：**批量工厂每次随机前强制以数据库为准，不再信任本地过期快照。
- **写时广播：**所有写操作成功后广播“词库已变更”事件，订阅方按需刷新。
- **阈值分流：**总量阈值 200 作为分水岭，200 以内同步刷新，200 以上写后防抖异步刷新，但读时（点随机）仍强制实时拉取以保证正确性。

### 6.2 架构变化

引入轻量事件总线或 `provide/inject`，新增可选的 `stores/library.ts` 作为长期收敛点（P3 阶段落地），短期先以事件 + 组件 `refresh` 暴露实现。

```
DimensionPanel ──emit(library:changed)──┐
LibraryDialog ──emit(library:changed)───┤
SegmentImportDialog ─emit(library:changed)┤─► App.vue 转发 ─► BatchFactory.refresh() / libraryStore.fetchAll()
DbRegistry 切换 ─emit(library:changed)──┘              └─► StatusBar 计数刷新（防抖）
                                        
BatchFactory.onRandom ──► 强制 await libraryStore.fetchAll() 或直连 dbGetAllModulesGrouped()
                       ──► randomAssembly(最新全量)
```

## 7 分阶段详细设计

### 7.1 P0 热修复（必做，1 个文件为主）

**问题：** `ensureDims` 的 early return 导致快照永不过期。

**改动：**

- 文件：`src/components/BatchFactory.vue`
- 删除 `if (dimensions.value.length) return` 守卫，改为每次可强制刷新。
- 新增 `refreshDims` 方法，内部并行拉取 `dbGetDimensions` 与 `dbGetAllModulesGrouped`，带 `loadingDims` 与 `try/catch` 保持现有降级语义。
- `onRandom` 首行改为 `await refreshDims()`，确保点击瞬间的范围实时。
- `defineExpose({ refresh: refreshDims })` 供 `App.vue` 主动刷新。

**伪代码：**

```ts
async function refreshDims(): Promise<void> {
  loadingDims.value = true
  try {
    const [dims, grouped] = await Promise.all([dbGetDimensions(), dbGetAllModulesGrouped()])
    dimensions.value = dims
    modulesByDim.value = grouped
  } catch {
    // jsdom 无 Tauri 时保持现有降级
  } finally {
    loadingDims.value = false
  }
}

async function onRandom(): Promise<void> {
  await refreshDims()
  // ... 原有 generate / generatePartial 逻辑不变
}
```

**收益：**单点改动即可让“新增后抽不到”消失，性能影响可忽略（本地 SQLite WAL，单次全量 < 10ms，500 条以内无感知）。

### 7.2 P1 事件同步（推荐与 P0 同批）

**问题：**双缓存失联，`App.vue:88` 的 `refreshStats` 未覆盖批量工厂。

**改动：**

- 选型：`mitt` 或 Vue 原生 `provide/inject`，本项目无额外依赖则优先 `mitt`（体积 < 1KB）或直接在 `App.vue` 用 `ref` 转发。
- `DimensionPanel.vue:101` `onDimConfirm`、`137` `onModuleConfirm`、`152` `onModuleUpdate`、`169` `onDeleteModule` 成功且 `await refresh()` 后各加一行 `emit('library:changed', { source: 'dimension-panel' })`。
- `App.vue:81-100` 新增对 `library:changed` 的监听，内部同时执行：
  ```ts
  await dimensionPanelRef.value?.refresh()
  await batchFactoryRef.value?.refresh()
  await refreshStatsCounts() // 轻量计数刷新
  ```
- 为 `BatchFactory` 在 `App.vue:266` 处加 `ref="batchFactoryRef"`。
- `LibraryDialog` 与 `SegmentImportDialog` 的 `@imported` 已有 `refreshStats`，保持并补上对 `BatchFactory` 的刷新，或统一走事件。

**正确性保障：**所有写后路径 `await` 串行，避免刷新竞态。

### 7.3 P2 切库一致性

**问题：** `src/stores/dbRegistry.ts` 切换前台库、重建 missing 库后，旧快照仍被使用。

**改动：**

- 在 `dbRegistry.switchActive` / `rebuildMissing` / `createBusiness` 成功后 `emit('library:changed', { source: 'db-registry' })`。
- `App.vue` 监听同样走 P1 的转发链路，或 `BatchFactory` 直接订阅。

### 7.4 P3 大库防抖异步（按你决策定制）

**决策原文：**词库总量增长到 200+ 之后再开始异步刷新总量，采用“修改行为后防抖的每十秒一次”。

**设计：**

- **阈值：** `moduleCount > 200` 时启用防抖分支，`<= 200` 时保持 P0/P1 的同步即时刷新。
- **触发：**写操作（CRUD / 导入）成功后，不再立即全量 `fetchAll`，而是将 `libraryStore` 标记为 `dirty = true` 并调度一次防抖任务。
- **防抖参数：** `wait = 10000ms`，`leading = false`，`trailing = true`。10 秒内多次修改仅合并为末尾一次全量拉取；`maxWait` 不另设，避免频繁抖动。
- **读时特例：**用户点击「随机生成」时无视防抖，强制 `await fetchAll()`，保证随机正确性不被防抖延迟。
- **计数刷新：**`StatusBar` 的 `dimCount / moduleCount` 同样走防抖，避免大库下每次敲击都重算总数。

**落地形态（二选一，推荐 A）：**

**A. 引入 `src/stores/library.ts`（长期更干净）：**

```ts
// stores/library.ts 概要
export const useLibraryStore = defineStore('library', () => {
  const dimensions = ref<Dimension[]>([])
  const modulesByDim = ref<Record<string, Module[]>>({})
  const total = computed(() => Object.values(modulesByDim.value).flat().length)
  const dirty = ref(false)
  let timer: number | null = null

  async function fetchAll() {
    const [dims, grouped] = await Promise.all([dbGetDimensions(), dbGetAllModulesGrouped()])
    dimensions.value = dims
    modulesByDim.value = grouped
    dirty.value = false
  }

  function scheduleFetch() {
    if (total.value <= 200) { void fetchAll(); return }
    dirty.value = true
    if (timer) clearTimeout(timer)
    timer = window.setTimeout(() => { timer = null; void fetchAll() }, 10000)
  }

  async function ensureFreshForRandom() {
    // 随机按钮专用：无视防抖，强制实时
    if (dirty.value || total.value > 200) await fetchAll()
    else if (!dimensions.value.length) await fetchAll()
  }

  return { dimensions, modulesByDim, total, dirty, fetchAll, scheduleFetch, ensureFreshForRandom }
})
```

- `DimensionPanel` 与 `BatchFactory` 改为消费 `libraryStore.dimensions / modulesByDim`，本地 `ref` 删除，彻底消除双缓存类型。
- 写操作后调用 `libraryStore.scheduleFetch()`，随机前调用 `await libraryStore.ensureFreshForRandom()`。

**B. 不引入新 store 的轻量版：**

- 在 `App.vue` 维护 `let debounceTimer: number | null` 与 `let pendingRefresh = false`，`library:changed`  handler 内判断 `moduleCount > 200` 则 `clearTimeout + setTimeout(refreshAll, 10000)`，否则立即 `await refreshAll()`。
- `BatchFactory.onRandom` 内加 `if (pendingRefresh) await refreshAll()` 分支。

**阈值与防抖的可观测性：**

- `StatusBar` 在防抖期间显示 `同步中…` 或 `· 10s 内同步` 的弱提示，避免用户误以为未保存。
- 控制台 `debug` 日志（仅 dev）：`[library] scheduleFetch dirty, total=2xx, debounce 10s`。

- mock `moduleCount = 250`，连续调用 5 次 `scheduleFetch`，断言 10 秒内仅发起 1 次 `dbGetAllModulesGrouped`，且 `dirty` 在 fetch 后清零。

## 10 风险与回滚

| 风险 | 概率 | 应对 |
|---|---|---|
| 每次随机多一次全量查询 | 低 | 本地 SQLite < 10ms；大库 200+ 场景随机仍强制实时，仅计数防抖 |
| 事件未订阅导致仍过期 | 低 | P0 已保证读时必新，事件仅为优化；单测覆盖事件链路 |
| 防抖期间用户误以为未生效 | 低 | StatusBar 弱提示 + 随机按钮不受防抖影响 |
| 回滚 | — | 纯前端 3 个 vue + 1 个 store，回滚即还原，无 DB 变更 |

## 11 验收标准

- [ ] A1 首次随机后新增词条，无需刷新页面即可被随机抽到。
- [ ] A2 删除词条后，随机不再出现已删除条目。
- [ ] A3 词库导入后，随机范围与导入后全量一致。
- [ ] A4 业务库切换后，随机范围与新前台库一致。
- [ ] A5 总量 <= 200 时写后即时刷新，总量 > 200 时写后 10 秒防抖合并，且随机按钮始终实时。

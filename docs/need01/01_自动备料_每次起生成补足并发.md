# 01 · 自动备料：每次起生成时补足并发

> 需求1｜改动域：`queue.rs::scheduler_loop` + `imageLoop.ts::refillFromEngine` + `ImageQueuePanel` 订阅（不改 UI 文案）

## 1. 现状 vs 目标

- **现状**（`queue.rs:724-730`）：仅当 `loop_enabled && running==0 && queued==0` 时 `emit hungry{want=concurrency}`，即“彻底饿死才一次性补 concurrency 条”。运行中 `queued` 从 N 耗到 0 的过程无补货，并发槽易空转。
- **目标**：运行中（`!stopped`），**每一次 `Queued→Running` 标记成功后**，检查 `queued_count < concurrency`，缺几补几：`want = concurrency - queued_count`，`emit hungry{want}`，前端随机 `want` 条推入等待列表。

## 2. 落点设计（后端为主，前端复用）

### 2.1 后端 `scheduler_loop`（`queue.rs:658-730`）

在 `taken==Some` 分支内、`spawn(worker)` 之后插入“起生成补货钩子”（伪代码）：

```rust
// A. 原有：running+1, emit_task, emit_stats, spawn worker（保持不动）
// B. 新增：top-up 检查（快照读，不跨 await 持锁）
let (loop_enabled, concurrency, queued_n, stopped2) = snapshot(...);
if loop_enabled && !stopped2 {
    let want = concurrency.saturating_sub(queued_n).min(concurrency);
    if want > 0 && should_emit_topup(&st, want) {
        let _ = app.emit(EVT_HUNGRY, HungryPayload { want });
    }
}
```

- `queued_n` = `count_queued(&st)` 在标记 Running **之后**重读（保证“起生成后”的排队数）。
- `should_emit_topup` 节流：`Mutex<Instant>` 记录上次 top-up emit 时间，`<800ms` 则跳过（与现有 hungry 后 `sleep 800ms` 同量级，避免高并发下burst）。饥饿兜底分支（724行）保留不动。
- `want` 钳制 `1..=concurrency`（≤8），与 `refillFromEngine` 的 `times` 钳制对称。
- 熔断/停止/自然结束时不 emit（`stopped` 检查在前）。

### 2.2 前端 `refillFromEngine`（`imageLoop.ts:245-288`）

**无需改随机逻辑**，仅确认两点（若不满足则小改）：

1. `shouldRefill(loopEnabled, running, want)` 已覆盖 top-up 场景（running=true, want>0 即补）。
2. 并发重入：top-up hungry 可能在上一次补货未完成时又来。加 `refillInflight` 计数合并——若已在补，累加 `pendingWant`（上限 concurrency），本轮结束后一次性再补，避免队列堆积重复 prompt。`cancelRefill/resetRefillCancel` 语义不变（停止时丢弃）。
3. 去重：`iq.enqueueBatch` 已有 `dedupeKeyOf` 去重，`skipped` 计入但不视为失败；top-up 补出重复属正常（toast 保持静默，只记日志）。

### 2.3 开关语义（重要，避免误伤）

- 总开关仍是 `loopEnabled`（“自动备料”勾选）。`autoRandomOnStart` 只管启动前 `prepareStartQueue`，本次**不改**。
- 若用户后续要求“两个开关合并”，另起需求；本期在 `ImageQueueSettings` 的 `loopEnabled` 旁加一行小字说明：“运行中每次起生成自动补足到并发量”。

## 3. 不动点

- 信号量/状态机/`can_transition`/`MAX_TASKS=2000` 不动；`prepareStartQueue`（启动前备料+confirm）不动。
- `HungryPayload{want}` 结构不动；`EVT_HUNGRY` 仍由后端 emit、前端 `ImageQueuePanel onMounted` 订阅。

## 4. 单测/自测要点

- Rust：`want` 计算表（concurrency=3：queued 0→want3；1→2；≥3→不emit）；节流 800ms 内二次起生成不重复 emit；stopped 熔断不 emit。
- TS：`refillFromEngine` 合并重入；`shouldRefill(false,·,·)=false`；停止后 hungry 到达被丢弃。
- 手工：并发=3，入队 3 条后启动，每完成一起生成观察 queued 回补到 3（运行条 `排队 N` 不归零）。

## 5. 验收（摘录，完整见 07）

- 并发 C 下运行中，任意时刻（除补货在途800ms内）`queued ≥ C` 或“已触发补货且在途”。
- 缺 K 条则一次 hungry `want==K`，前端随机 K 次逐条 `enqueueBatch`（去重跳过不崩）。
- 关闭 `loopEnabled` 即回现状（仅饿死补货）。

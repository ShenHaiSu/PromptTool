# 02 · 文件名预占位与反查

> 需求2a+2b｜改动域：`ImageTask` 结构 + `iq_enqueue/worker/download_and_persist` + `ImageTaskCard/DetailDialog` + `ImageQueuePanel` 搜索条

## 1. 预占位（2a）

### 1.1 为什么入队即占位

现状文件名在下载完成后才生成（`download_and_persist:573-580`），`seq` 取“当日已建数+1”，`ext` 取 content-type。测试要求“card  visible 即有文件名”，故必须**入队时先占 stem，完成时补 ext/碰撞后缀并回写**。

### 1.2 字段（`queue.rs:106-126 ImageTask` 新增，全部 `Option` + serde `default`）

```rust
pub expected_stem: Option<String>, // 预占：20260924_230024_039_1K_3-4_50e9cce9（无扩展名）
pub filename: Option<String>,      // 落盘确定：xxx.png（含碰撞 -N 后缀）
```

- `file_path` 已有，完成时与 `filename` 一起回写并 `emit_task`。
- TS `ImageTaskView` 同步加 `expectedStem?: string|null; filename?: string|null`（`lib/imageQueueApi.ts`）。

### 1.3 占位算法（复用 `build_image_filename`，拆两步）

- 入队（`iq_enqueue` 内逐条）：`date_prefix=Local::now(%Y%m%d_%H%M%S)`，`seq=同state当日计数+1`（把现有 `same_day_count` 逻辑抽为 `next_day_seq()`，入队与落盘共用；入队时即 +1 占位，避免并发重号——占位 bodies 在 `tasks/order` 锁内完成）。
- `stem = build_image_filename(...).trim_end(ext)` 即去掉 `.{ext}` 部分：用 `prompt_hash8(prompt)+size+ratio` 先拼 `stem`，ext 先空。
- 落盘（`download_and_persist`）：content-type 定 `ext` 后，`stem + .ext` 经 `unique_filename_in` 判重；若被加 `-N`，`filename` 取实际名（预占与实际不一致属正常，卡片以 `filename ?? expectedStem+.*` 显示）。

### 1.4 前端展示

- `ImageTaskCard` 状态行下新增一行 `mono` 文件名：`filename ?? expectedStem+'.…'` + 复制按钮（复用 `onCopy` 模式，`data-testid=image-task-filename-<id>`）。
- `ImageTaskDetailDialog` 同步显示 `expectedStem/filename/filePath` 三行；`filePath` 点击走 `dbRevealInExplorer` 定位。
- 虚拟列表 `estimateSize 110` 可能需调到 128（卡片增高一行，`ImageQueuePanel:87`）。

## 2. 反查（2b）

### 2.1 后端 `iq_find_by_filename(query: String) -> Option<ImageTask>`

归一化：`trim → 取 basename（去目录）→ 去首尾引号 → lower`；匹配顺序：

1. `filename` 全等（大小写不敏感）；
2. `file_path` 后缀匹配；
3. `expected_stem` 匹配（支持不带扩展名查）；
4. 去碰撞后缀再比（`xxx-1.png → xxx.png`  stemming 后比 stem）。

内存 `tasks` 扫描即可（2000 上限，O(n) 足够）；找不到返回 `None`（前端 toast“未找到”，不抛错）。

### 2.2 前端入口（“合适位置”定案）

- **主入口**：`ImageQueuePanel` 运行条右侧（配置按钮左侧）加 `input[data-testid=iq-filename-search] + button[data-testid=iq-filename-go]`，placeholder `文件名反查…（支持 stem/全名）`，回车=点击。
- 命中：`virtualizer.scrollToIndex(order.indexOf(id))` + 高亮该卡 2s（加 `ring` class）+ 自动 `openDetail`；未命中 toast warning。
- 次入口：`ImageTaskDetailDialog` 文件名旁“复制”已覆盖去文件管理器方向，无需再加。

## 3. 不动点

- 命名公式/哈希/`unique_filename_in` 碰撞规则不动；`embed` 内嵌 meta 不动（`taskId` 已在 meta 内，反查与内嵌互为冗余）。
- 历史任务（已 `clearFinished`）查不到属预期，toast 文案注明“已清理的任务无法反查”。

## 4. 自测要点

- 入队 3 条即见 3 个不同 stem；完成 1 条后 `filename` 有 ext 且文件存在；重名碰撞（同 prompt 同秒）出现 `-1` 后缀且两 card 文件名不同。
- 反查：全名/大小写混写/不带 ext/带 `-1` 后缀/绝对路径粘贴，五种皆命中；乱串 toast 不崩。
